# Security scanning

This project uses complementary checks. They answer different questions and do
not replace one another.

| Tool | What it checks | When it runs |
| --- | --- | --- |
| Ruff and Black | Python correctness, imports, and formatting | Pre-commit |
| Semgrep | Risky source-code, Dockerfile, and configuration patterns | Pull requests and pushes to `main` |
| Trivy | Packages and operating-system layers in the built Docker image | Pull requests and pushes to `main` |
| SonarQube | Code quality, security rules, and project reporting | Optional local server or CI when configured |
| OWASP ZAP | Runtime HTTP headers, cookies, and passive web findings | CI against an isolated app; opt-in local scan |

## Semgrep versus CodeQL

Semgrep is the default source-security scanner because this repository combines
Python, browser JavaScript, Docker, and configuration files. It is fast and
rule-driven, so it is suitable for every pull request. CodeQL is a strong
alternative for deep, GitHub-native data-flow analysis, but does not replace
Trivy's image scan and adds a heavier language-specific build step.

## CI checks

`.github/workflows/security.yml` runs:

1. `semgrep scan --config auto --error`, which fails on matching security
   findings.
2. A Docker build followed by Trivy. Trivy fails only for **fixable** high or
   critical vulnerabilities, avoiding a block for CVEs with no available fix.
3. SonarQube only when both repository secrets below exist:
   - `SONAR_HOST_URL` — for example, `http://sonarqube.internal:9000`
   - `SONAR_TOKEN` — a token generated by that SonarQube server

4. OWASP ZAP starts a fresh CI-only application stack, waits for `/health`, and
   runs a one-minute **passive baseline** scan. Its HTML and JSON reports are
   uploaded as the `zap-baseline-report` workflow artifact. Warnings are
   reported without failing the build; a ZAP execution failure does fail it.

## Local SonarQube

Start the optional service without changing the normal app stack:

```powershell
just security-up
```

With Docker Desktop and Make instead:

```sh
make security-up
```

The equivalent direct Podman command is:

```powershell
podman compose --project-name autopilot-security -f docker-compose.security.yml --profile security up -d
```

Open `http://localhost:9000`, complete initial setup, create an `autopilot`
project token, then scan the checkout:

```powershell
docker run --rm -e SONAR_HOST_URL=http://host.docker.internal:9000 -e SONAR_TOKEN=YOUR_TOKEN -v "${PWD}:/usr/src" sonarsource/sonar-scanner-cli
```

When using Podman rather than Docker Desktop, replace `host.docker.internal`
with `host.containers.internal`.

Stop the local service while preserving its data:

```powershell
just security-down
```

Docker Desktop equivalent:

```sh
make security-down
```

## Local Semgrep

Run the same source and configuration scan used by CI:

```powershell
just semgrep
```

Docker Desktop equivalent:

```sh
make semgrep
```

It mounts this checkout read-only and excludes local caches. Semgrep exits
non-zero when it finds a rule match.

## Local Trivy

Build and scan the same artifact that CI scans:

```powershell
docker build -t applypilot:local .
docker run --rm aquasec/trivy:latest image --severity HIGH,CRITICAL --ignore-unfixed applypilot:local
```

Use `--exit-code 1` when you want the local command to fail on findings, as CI
does.

## OWASP ZAP

ZAP is dynamic application security testing (DAST): it observes a running web
application rather than reading source or image layers. It therefore complements
Semgrep and Trivy, but needs a safe target.

Start this project's local app, then run the passive baseline scan:

```powershell
just start
just zap-baseline
```

With Docker Desktop and Make, start the app then scan it:

```sh
make start
make zap-baseline
```

The command joins the local `autopilot_default` Podman network and targets the
private Compose hostname `http://app:8000`. It spiders for one minute and checks
passive findings such as insecure headers and cookie settings. It does **not**
send SQL-injection, XSS, or other attack payloads.

ZAP returns exit code `2` when it finds warnings. The local `just zap-baseline`
command treats that as a completed scan and prints the findings; exit code `3`
still indicates a scanner failure.

To prevent a stalled local scan, the command stops ZAP after 150 seconds and
reports that timeout as a failure.

For active SQLi/XSS testing, use ZAP's full/API scan only against a disposable
staging environment with test accounts and explicit authorization. Do not point
an active scan at production.
